Hi — I've been working on the same problem independently (optimized EPUBs losing their KOReader sync identity), and I have a version running on my own device, so I hope a few notes from that experience are useful rather than noise. This is your draft and your design; treat all of this as observations, not requests.

First, on the storage choice: putting the id in an OPF `<meta>` is the more conventional call, and reading it through the existing `ContentOpfParser` pass so it lands in `BookMetadataCache` is genuinely cheaper than what I did — mine reopens the archive on every sync, yours pays once at scan time. I went with a separate `META-INF` entry mainly because tools that regenerate `content.opf` (Calibre conversions and metadata edits especially) tend to drop `meta` elements they don't recognise, so the id doesn't always survive a round trip through them. I don't think either choice is simply right; they trade different failure modes, and yours avoids the per-sync cost mine pays.

Two things I ran into that I didn't see handled in the diff — I may be misreading it, so please correct me:

**Re-optimizing an already-optimized book.** As far as I can tell the hash is recomputed unconditionally from whatever file is handed to the optimizer. If someone optimizes a book that already carries an id, that recomputation captures the hash of the *already-optimized* bytes and overwrites the original's id — after which pairing with the untouched original (on a phone, say) is broken permanently, and silently. It's an easy case to hit by accident with a batch. I ended up detecting an existing id and preserving it verbatim rather than recomputing.

**Coordinate space when applying a remote position.** This one depends on how much your optimizer restructures content. The embedded id names the pre-optimization original, but the file the reader is holding has been rewritten — and if the optimizer splits long sections, the two no longer share a structure. When I substituted the id without also changing how remote positions map, applied positions could land somewhere other than where the other device actually was. I had to distinguish "this id refers to this file's own bytes" from "this id refers to the original this file came from", and map positions in the source document's space for the latter. If your optimizer only re-encodes images, this may not bite you at all — but it's worth checking before it becomes a bug report about sync landing on the wrong page.
